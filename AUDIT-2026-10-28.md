## 2. Audit possible sans les sources

### 2.1 Codes d'erreur USB
Les définitions de `IOKit/IOReturn.h` confirment ces correspondances :
- `0xE00002D6` = `kIOReturnTimeout` (code 0x2D6). Aucune donnée n'est arrivée dans le délai.
- `0xE00002EB` = `kIOReturnAborted` (code 0x2EB). La requête a été annulée à l'arrêt.

L'interprétation du programme était donc correcte.

### 2.2 Le paquet de loopback est valide
`01 20 | 10 00 | 5769695550726F4D616300 55AAFF1234` :
- handle 0x001 ;
- PB=2, BC=0 ;
- longueur 0x0010 = 16 octets. La charge utile fait 11 + 5 = 16 octets.

Le format est correct. En loopback local, le contrôleur doit renvoyer ce paquet sur bulk-IN 0x82. Il ne revient pas. **Le problème se situe donc entre le contrôleur et l'hôte, pas dans le protocole de la manette.** Le L2CAP de la manette n'a jamais été testé de façon valable.

### 2.3 Hypothèse principale : firmware Realtek non chargé
La lecture HCI donne `manufacturer=0x005D` (Realtek) et `subversion=0x8761`. Le BT500 contient donc une puce **Realtek RTL8761B(U)**. Elle n'est pas connue d'Apple, et macOS ne lui envoie aucun firmware.

Sous Linux, le pilote `btrtl` télécharge toujours un patch au démarrage : `rtl_bt/rtl8761bu_fw.bin` et `rtl8761bu_config.bin` du paquet linux-firmware. Il passe par la commande constructeur `0xFC20`, en blocs de 252 octets maximum. Sur le firmware ROM d'origine, les commandes et événements HCI fonctionnent souvent : c'est le cas de la recherche, du nom distant et de la connexion ACL. Le chemin des données ACL est en revanche réputé peu fiable ou incomplet.

Ce scénario correspond exactement aux observations :
- les événements arrivent sur interrupt-IN ;
- les crédits ACL reviennent ;
- bulk-IN ne renvoie jamais rien, même en loopback ;
- la manette se déconnecte après environ 10 s (raison 0x13) faute de réponse L2CAP.

**Hypothèse non démontrée.** Le test le moins coûteux pour la valider :
1. charger le firmware avec `0xFC20` ;
2. relire Local Version (la sous-version ou la révision doit changer) ;
3. relancer **le loopback seul**.

Ce test ne doit rien coûter d'autre tant que le loopback échoue.

Autres causes de transport à vérifier dans `Diagnostics/USBCapture/main.m` quand l'archive sera disponible :
- lecture bulk-IN lancée sur le bon objet pipe (adresse 0x82) ;
- tampon lu d'une taille multiple de `wMaxPacketSize` ;
- lectures lancées *avant* l'envoi du paquet ;
- `alternate setting` 0 réellement sélectionné sur l'interface 0.

### 2.4 Nouveau fait : Dolphin accepte déjà le nom de la manette
Dans le code source de Dolphin (`Source/Core/Core/HW/WiimoteReal/WiimoteReal.cpp`, branche master) :

```cpp
// IsWiimoteName
return name.starts_with("Nintendo RVL-CNT");
```

« Nintendo RVL-CNT-01-UC » commence par ce préfixe. Sur macOS, Dolphin se connecte aux Wiimotes réelles via IOBluetooth avec le **Bluetooth interne** : il ouvre lui-même les canaux L2CAP 0x11 et 0x13. Ce chemin pourrait donc fonctionner avec la manette **sans dongle ni pilote**.

Limite : le jeu verrait une Wiimote avec une extension inconnue (ID Pro Controller). Mario Kart Wii / Retro Rewind ne l'utiliserait pas directement comme Classic Controller. Ce n'est donc pas une solution, mais **un test sans code de faisabilité de la liaison**.

## 3. Choix d'architecture recommandé

### Sortie vers Dolphin : serveur DSU (protocole « cemuhook », UDP)
- Dolphin intègre un client DSU (`InputCommon/ControllerInterface/DualShockUDPClient`). Il n'y a **aucun `#ifdef` de plateforme**, donc il est actif sur macOS.
- Configuration : *Contrôleurs → Sources d'entrée alternatives → DSU Client*, avec un serveur `127.0.0.1:26760`.
- Entrées exposées : croix directionnelle, 4 boutons de face, L1/R1/L2/R2, L3/R3, Share/Options/PS, deux sticks analogiques, plus la batterie.
- Cela couvre toute la manette Wii U Pro. On peut ensuite l'associer à un Classic Controller ou à une Wiimote + Nunchuk émulés dans Dolphin.
- **Aucun entitlement restreint, aucun DriverKit, aucun compte payant.** Un programme en espace utilisateur signé ad hoc suffit. Il peut tourner en LaunchAgent.

Pistes écartées comme premier choix :
- `IOHIDUserDevice` (HID virtuel) demande l'entitlement `com.apple.developer.hid.virtual.device`.
- Un dext DriverKit HID demande les entitlements `driverkit.*`.
- Ces deux pistes risquent de rencontrer le même refus que l'erreur Xcode du §9, sans vérification préalable. Un kext est hors de question.

### Entrée : deux voies, par ordre de coût
**A. Bluetooth interne + IOBluetooth (recommandée en premier).**
- Le programme ouvre les canaux L2CAP 0x11 et 0x13 vers `8C:CD:E8:BB:0D:58` avec `IOBluetoothDevice openL2CAPChannelSync`, comme le fait Dolphin.
- Il initialise l'extension : écriture de `0x55` en `0xA400F0`, puis de `0x00` en `0xA400FB`.
- Il passe en mode de rapport `0x3D` et décode les sticks et les boutons.
- Rien à charger, pas de root, pas de dongle. Il faut seulement l'autorisation Bluetooth (TCC).
- Le dossier cite `BluetoothManager.swift` / `NintendoL2CAPManager.swift`, mais **ne dit pas pourquoi cette voie a été abandonnée**. Il faut retrouver ce résultat avant de la refaire.

**B. Dongle BT500 en espace utilisateur (IOUSBHost, root).** Seulement si la voie A est impossible :
- chargement du firmware Realtek (§2.3) ;
- loopback validé ;
- L2CAP minimal + HID sur ACL.

Cette voie est plus lourde, et il faudrait vérifier le réattachement du dongle.

La VM Linux/QEMU n'est à garder qu'en dernier recours. Elle ajoute une couche de transport (Linux → macOS) qui n'existe pas encore.

## 4. Prochaines étapes concrètes (les moins coûteuses d'abord)

1. **Sur la machine d'origine :** copier l'archive `/private/tmp/…tar.gz` et les journaux dans un endroit durable, puis les transmettre.
2. **Test sans code de la voie A :**
   1. installer Dolphin ;
   2. *Contrôleurs → Wii Remote 1 → « Wii Remote réelle »* ;
   3. activer la recherche continue ;
   4. appuyer sur SYNC.

   Si les LED cessent de clignoter et que la manette reste connectée, la liaison L2CAP sur le Bluetooth interne fonctionne. On passe alors au lecteur IOBluetooth + serveur DSU.
3. Selon le résultat : prototype « lecteur IOBluetooth → serveur DSU ». **Preuve minimale exigée** : un bouton pressé apparaît dans la configuration des commandes de Dolphin, via le périphérique `DSUClient/0/…`.
4. Si la voie A échoue : test du firmware Realtek puis loopback (§2.3), avec le dongle branché.

Matériel nécessaire pour la suite : la manette (et le dongle pour la voie B) sur ce Mac. Xcode n'est pas indispensable : `swiftc` des Command Line Tools suffit pour un outil en ligne de commande.
